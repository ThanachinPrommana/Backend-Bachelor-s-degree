## Problem Statement

จากฝั่งผู้ใช้งาน (ผู้ขาย) พบปัญหาหลัก 2 ประการเมื่อต้องการลงประกาศขายบ้าน:
1. **คอขวดระหว่างการอัปโหลดไฟล์ (Backend)**: เมื่อทำการโพสต์ขายบ้านพร้อมแนบรูปภาพ (สูงสุด 5 รูป) และวิดีโอ (สูงสุด 2 ไฟล์) ผู้ใช้ต้องรอโหลดหน้าจอเป็นเวลานานมาก เนื่องจากระบบเดิมทำการอัปโหลดไฟล์ขนาดใหญ่ขึ้น Cloudinary เรียงลำดับ (Synchronous) ให้เสร็จทั้งหมดก่อนจึงจะสามารถทำงานขั้นต่อไปและแจ้งผลกลับไปยังผู้ใช้ได้
2. **ความสับสนในการกรอกช่องทางติดต่อ (Frontend)**: ในหน้ากรอกข้อมูลผู้ขาย (PostInform) ผู้ใช้มักจะกรอกแค่ Line ID หรือชื่อผู้ใช้ Facebook แต่ระบบต้องการรูปแบบลิงก์เต็ม (URL) การแปลงค่าของระบบแบบเดิม (Sanitization) จะเติมแค่ `https://` นำหน้า ID ซึ่งทำให้ลิงก์นั้นใช้งานไม่ได้จริงและเกิดความผิดพลาดเมื่อผู้ซื้อพยายามคลิก

## Solution

1. **ปรับปรุงการอัปโหลดไฟล์ให้เป็นแบบ Asynchronous**: ระบบจะรับไฟล์จากผู้ใช้มาเก็บไว้ชั่วคราวบนเซิร์ฟเวอร์ (Local/Memory) เพื่อให้ Controller นำข้อมูลไปสร้างประกาศและส่งผลลัพธ์ว่า "สำเร็จ" คืนให้ผู้ใช้ได้ทันที จากนั้นระบบจะใช้ Background Job นำรูปภาพและวิดีโอไปอัปโหลดขึ้น Cloudinary แบบคู่ขนาน (Promise.all) เมื่อเสร็จสิ้นจึงจะอัปเดต URL กลับเข้าฐานข้อมูลของโพสต์นั้น
2. **ระบบวิเคราะห์และเติม URL โซเชียลมีเดียอัตโนมัติ**: ก่อนจะบันทึกข้อมูล หากผู้ใช้กรอกข้อความที่ไม่มี `http://` หรือ `https://` ระบบจะวิเคราะห์ว่านี่คือ ID/Username และทำการเติมโครงสร้าง URL ของแพลตฟอร์มนั้นๆ ให้โดยอัตโนมัติ (เช่น สำหรับ Line จะเติม `https://line.me/ti/p/~` และ Facebook จะเติม `https://facebook.com/`)

## User Stories

1. As a seller, I want to กดปุ่มยืนยันการลงประกาศแล้วได้รับข้อความ "โพสต์สำเร็จ" ในทันที, so that ฉันไม่ต้องทนนั่งรอหน้าจอโหลดเป็นนาทีจนกว่ารูปภาพทั้งหมดจะอัปโหลดเสร็จ
2. As a seller, I want to พิมพ์เพียงแค่ Line ID ลงในแบบฟอร์ม, so that ฉันไม่ต้องไปค้นหาวิธีสร้างลิงก์ Line ด้วยตัวเองให้ยุ่งยาก
3. As a seller, I want to พิมพ์เพียงแค่ชื่อ Facebook ลงในแบบฟอร์ม, so that ฉันไม่ต้องไปก๊อปปี้ URL แบบเต็มๆ มาแปะให้วุ่นวาย
4. As a buyer, I want to คลิกที่ปุ่มติดต่อผู้ขายผ่าน Line/Facebook ในโพสต์, so that ฉันสามารถแชทพูดคุยกับผู้ขายผ่านแอปพลิเคชันได้ทันทีโดยไม่เจอปัญหาลิงก์เสีย
5. As an administrator, I want to ให้รูปภาพและวิดีโอถูกทยอยอัปโหลดแบบเบื้องหลัง (Background), so that เซิร์ฟเวอร์สามารถคืน Connection ให้กับ Client ได้เร็วขึ้นและรองรับโหลดได้มากขึ้น

## Implementation Decisions

- **การรับไฟล์ (Backend)**: เปลี่ยน Middleware ของ Multer จาก `multer-storage-cloudinary` มาเป็นการเก็บแบบ `multer.diskStorage()` (หรือ memoryStorage) ในโฟลเดอร์ชั่วคราว
- **Controller Post Creation (Backend)**:
  - แยกการสร้าง PropertyPost ออกจากการอัปโหลดขึ้น Cloudinary
  - Response กลับหา Frontend (HTTP 201) ทันทีที่บันทึกข้อมูล Post (Text) สำเร็จ
  - สั่งรัน Async Function แบบไม่ Await (หรือรันคิว) สำหรับส่งภาพไปอัปโหลดขึ้น Cloudinary ด้วย `cloudinary.uploader.upload` (ใช้ `Promise.all` เพื่ออัปโหลดขนานกัน)
  - หลังจากอัปโหลดเสร็จ จะบันทึก `secure_url` ลง Table `Image` และ `Video` พร้อมลบไฟล์ชั่วคราวทิ้ง
- **ระบบแปลง URL (Frontend)**: ปรับ Logic ในฟังก์ชันของไฟล์ `PostInform.jsx` ให้ฉลาดขึ้น เช็คการมีอยู่ของ `http` เป็นหลัก หากไม่มีให้เติม Prefix:
  - Line: `https://line.me/ti/p/~`
  - Facebook: `https://facebook.com/`
- **User Interface (Frontend)**: อาจจะมีการแสดงแจ้งเตือนหรือ Alert บอกผู้ขายในหน้า PostDetail ว่า "รูปภาพกำลังถูกประมวลผล" หากผู้ใช้รีเฟรชมาดูเร็วเกินไปและรูปยังอัปโหลดไม่เสร็จ (Option เสริม)

## Testing Decisions

- การทดสอบจะเน้นไปที่พฤติกรรมของการตอบสนองจาก API ว่าจะต้องได้ Response กลับมาเร็วกว่าหลักเสี้ยววินาทีหลังจากกดสร้างโพสต์
- ทดสอบว่าไฟล์ชั่วคราว (Temp files) จะต้องถูกลบทิ้งเมื่อการทำงาน Background Job เสร็จสิ้น (ป้องกัน Disk เต็ม)
- ทดสอบว่าการกรอกข้อมูล Line ID ทั้งแบบที่มีเครื่องหมาย `@` และไม่มีเครื่องหมาย `@` รวมถึงการกรอก URL แบบเต็มมาอยู่แล้ว จะต้องถูกประมวลผลออกมาเป็นลิงก์ที่คลิกใช้งานได้จริง (Clickable) โดยไม่มีบัคซ้อน `https://https://`

## Out of Scope

- ไม่ครอบคลุมการทำระบบ Notification เด้งเตือนผู้ใช้เมื่อรูปภาพถูกอัปโหลดเสร็จสมบูรณ์
- ไม่ครอบคลุมการรีไซส์รูปภาพ (Image Resizing/Compression) ฝั่ง Frontend แบบหนักๆ ในรอบนี้ (ใช้ขนาดที่ผู้ใช้อัปโหลดเข้ามาเป็นหลัก)
- การทำ Retry Policy (กรณี Cloudinary ล่ม) อาจจะใส่ไว้เป็นแค่การ log error พื้นฐาน ยังไม่ทำ Message Broker อย่าง RabbitMQ เพื่อการทดลองโพสต์ซ้ำ

## Further Notes

- การทำ Background Upload แบบไม่ใช้ Message Broker จำเป็นต้องระมัดระวัง Node.js process restart กลางคัน หากเซิร์ฟเวอร์ดับระหว่างอัปโหลดรูป รูปภาพในโฟลเดอร์ชั่วคราวจะค้างอยู่และ Database จะไม่มีรูปภาพ (ควรมี CRON Job เล็กๆ เคลียร์ไฟล์ขยะในอนาคต)
